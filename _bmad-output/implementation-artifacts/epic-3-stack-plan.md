# Epic 3 – stacked PR plan

## TL;DR

- Epic 3 ("Shared configuration store, operator CLI and release") ships as a **linear stack of 4 PRs** on `wixyvir/cvestream`: `main <- 3.1 <- 3.3 <- 3.2 <- 3.4`, i.e. `main <- wixyvir/cvestream#22 <- wixyvir/cvestream#21 <- wixyvir/cvestream#23 <- <3.4 PR>` (see the Status section).
- Story 3.4 (Valkey administration UI, wave 11) was added on 2026-11-07 by a course correction (`planning-artifacts/sprint-change-proposal-2026-11-07-valkey-admin-ui.md`). Its PR sits on top of 3.2; 3.1, 3.3 and 3.2 can merge without waiting for it.
- Each PR's base is the story below it, so each PR diff shows **only that story's changes**. The 3.1 PR also carries this plan.
- The stack is not in story-number order on purpose: **3.3 (release, Kubernetes) sits below 3.2 (operator CLI)** because it only needs 3.1's `deploy/valkey/` files, so you can test it earlier; 3.2 needs 3.1's Valkey provider and nothing from 3.3.
- Schedule: 3.1 and 3.3 are created and developed **concurrently** (wave 9). 3.1 is reviewed first; 3.3 is then rebased onto the reviewed 3.1 and reviewed. 3.2 (wave 10) starts from the reviewed 3.1 branch and is developed while 3.3 is rebased and reviewed; it is then rebased onto the reviewed 3.3, its PR retargeted to the 3.3 branch, and reviewed.
- Each PR goes through three automated steps: `bmad-create-story` (story file + draft PR), `bmad-dev-story` (implementation pushed on the PR), `bmad-code-review` (patches applied, open decisions posted as inline review comments, PR marked ready).
- You test the PRs one at a time, bottom-up (3.1, then 3.3, then 3.2, then 3.4): `git switch <branch>`, run the gates, then the manual checks listed per story below. 3.1 needs Docker (a disposable Valkey); 3.3 reuses the minikube harness from `origin/test-early-k8s`.
- Look at the inline review comments marked "decision needed" on each PR: they are the choices the agent did not make for you.
- Merge bottom-up only, with a regular merge (not squash): 3.1, then 3.3, then 3.2, then 3.4. Nothing pushes a `v*` tag or creates a GitHub Release: the first release is yours, after the merges.

### Why this order: `main <- 3.1 <- 3.3 <- 3.2 <- 3.4`

`sprint-status.yaml` puts 3.1 and 3.3 in wave 9 and 3.2 in wave 10:

- 3.1 needs 1.3 and 1.6 (on `main`).
- 3.3 needs only 1.6 (on `main`), **plus** one file-level dependency recorded in the wave 9 caveat: the example Valkey `StatefulSet` must mount `deploy/valkey/valkey.conf` and `users.acl`, which 3.1 writes. So 3.3 must sit on top of 3.1, but it needs none of 3.1's Python code.
- 3.2 needs 1.3 and **3.1's provider** (the CLI writes through it). It needs nothing from 3.3.

Two linear orders are possible, `3.1 <- 3.2 <- 3.3` and `3.1 <- 3.3 <- 3.2`. The second is chosen because:

1. 3.3 is ready earlier (wave 9, developed alongside 3.1), so it can be reviewed and tested before 3.2 is even developed. Putting it on top of 3.2 would hold a finished PR behind a later one.
2. 3.3 is mostly YAML (workflow, manifests, docs) and touches little Python, so 3.2 rebasing onto it is cheap. The reverse (3.3 rebasing onto 3.2's CLI) would gain nothing.
3. You can merge 3.1 and 3.3 without waiting for 3.2, and cut a first release with the Valkey provider and the Kubernetes manifests; the CLI follows.

Consequence: on the 3.3 branch, the operator CLI does not exist yet. 3.3's manual tests seed Valkey with `valkey-cli` (the documented contract from 3.1), not with `cvestream config import`.

## 2. How the PRs are produced

Each story goes through three autonomous steps, in its own git worktree (`.worktrees/<branch>`):

1. **`bmad-create-story`**: writes the story file `_bmad-output/implementation-artifacts/<story-key>.md` (ACs, tasks, dev notes drawn from the architecture and from this plan), sets the story to `ready-for-dev` in `sprint-status.yaml` (and `epic-3` to `in-progress`), commits it (`docs(story-3.x): ...`) on the story branch and opens a **draft PR** against its base. Title follows Conventional Commits with the story ID, e.g. `feat(story-3.1): add the Valkey configuration provider`.
2. **`bmad-dev-story`**: implements the tasks on the same branch, with commits separated by concern (`feat(story-3.x)`, `test(story-3.x)`, `docs(story-3.x)`, `chore(story-3.x)`, `ci(story-3.x)`, `build(story-3.x)`), runs the local gates (including the `valkey` tests against a disposable container and `kubectl kustomize` once `deploy/k8s` exists), sets the story to `review` and pushes to the same PR.
3. **`bmad-code-review`**: adversarial review (Blind Hunter, Edge Case Hunter, Acceptance Auditor). Then:
   - clear-cut fixes (**patches**) are applied and pushed as extra commits (`fix(story-3.x): ...`);
   - **findings that need your decision** are posted as **inline PR review comments** on the relevant lines (marked `:factory:`), with the options and the reviewer's recommendation;
   - deferred or dismissed items are listed in the story file's review section;
   - the PR is marked **ready for review**.

Gates on this machine: `docker build --target runtime` fails pulling `ghcr.io` images with an x509 error (the Docker daemon does not trust the proxy CA). The automation tries it once, reports it, and relies on the PR's `ci` check, which builds the image on GitHub.

Commits are never squashed. Nothing is merged, nothing is pushed to `main`, no `v*` tag is pushed and no GitHub Release is created by the automation. Merging and releasing are up to you.

## 3. How to test, story by story

Run the stories in stack order (3.1, 3.3, 3.2, 3.4). Each branch already contains everything below it.

### Common gates (every story)

```bash
git fetch origin
git switch <branch>
uv sync --locked
uv run ruff check
uv run ruff format --check
uv run ty check
uv run lint-imports
uv run pytest
uv run cvestream config schema --check
uv run cvestream config validate endpoints.example.yaml
kubectl kustomize deploy/k8s/overlays/example >/dev/null   # 3.3 and 3.2 only
docker build --target runtime -t cvestream:test .            # fails here behind the proxy: rely on CI
```

Expected: all green. `pytest` runs with the network blocked (pytest-socket), `live` tests deselected. Also check that the PR's `ci` check is green on GitHub, since it is the merge gate, and that its log shows the `valkey` tests **running, not skipped** (from 3.1 on).

#### A disposable Valkey (3.1 and 3.2)

`valkey-cli` is not installed on the host; use the one inside the container. The exact mount points and password provisioning are whatever 3.1 documents in `docs/config-contract.md` and `compose.yml`; the shape is:

```bash
docker run -d --rm --name cvs-valkey-manual -p 127.0.0.1::6379 \
  -v "$PWD/deploy/valkey:/usr/local/etc/valkey:ro" \
  valkey/valkey:9.1 valkey-server /usr/local/etc/valkey/valkey.conf
docker port cvs-valkey-manual 6379          # -> 127.0.0.1:<port>
vcli() { docker exec -i cvs-valkey-manual valkey-cli "$@"; }   # vcli --user <u> --pass <p> <cmd>
# afterwards: docker stop cvs-valkey-manual
```

A random host port (`-p 127.0.0.1::6379`) avoids clashing with another Valkey. Use `docker pause` / `docker unpause` to simulate an outage: a restart would change the port.

## 4. Merge order and propagation

**Merge bottom-up only:** 3.1, then 3.3, then 3.2, then 3.4. Each merge needs a green `ci`. Use a regular merge (not squash) so that the upper branches keep sharing history with `main`.

**After merging 3.1 into `main`:** if "Automatically delete head branches" is enabled (or you delete the branch), GitHub retargets the 3.3 PR to `main`. Otherwise:

```bash
SSL_CERT_FILE=$HOME/ca.pem gh pr edit story-3-3-release-and-kubernetes-deployment --base main --repo wixyvir/cvestream
```

**After merging 3.3 into `main`:** same for 3.2 (`--base main`).

**After merging 3.2 into `main`:** same for 3.4 (`--base main`). On a change to a lower story, rebase 3.4 last, onto the 3.2 branch.

**If a lower story changes after the upper ones exist** (review fix, decision applied), rebase upwards in order, 3.3 then 3.2:

```bash
git fetch origin
git switch story-3-3-release-and-kubernetes-deployment
git rebase origin/story-3-1-valkey-configuration-provider
# on a uv.lock conflict: take the base's version, then regenerate
git checkout --ours uv.lock && uv lock && git add uv.lock && git rebase --continue
uv sync --locked && uv run pytest && kubectl kustomize deploy/k8s/overlays/example >/dev/null
git push --force-with-lease

git switch story-3-2-operator-cli-for-endpoints-products-and-tokens
git rebase origin/story-3-3-release-and-kubernetes-deployment
uv sync --locked && uv run pytest
git push --force-with-lease
```

- During a rebase, `--ours` is the branch being rebased onto (the base). Keep that `uv.lock`, run `uv lock`, then continue. Never merge `uv.lock` by hand.
- On a `sprint-status.yaml` conflict, keep every story's status line (the base's for the lower stories, the rebased branch's for its own).
- On `ci.yml`, keep both the Valkey service (3.1) and the Kustomize step (3.3) in the one `ci` job.
- If a lower branch was **rewritten** (rebased, or squash-merged into `main`), use `--onto` so that its old commits are not replayed:
  ```bash
  git rebase --onto origin/main <old-3.1-tip> story-3-3-release-and-kubernetes-deployment
  git rebase --onto origin/story-3-3-release-and-kubernetes-deployment <old-3.3-tip> story-3-2-operator-cli-for-endpoints-products-and-tokens
  ```
- Always push with `git push --force-with-lease`, never plain `--force`. Never push to `main`.

**After the four merges** (3.4 last; 3.1 to 3.2 may merge without waiting for it, and `epic-3` stays `in-progress` until 3.4 is `done`): set `epic-3: done` in `sprint-status.yaml` (and run the optional retrospective).

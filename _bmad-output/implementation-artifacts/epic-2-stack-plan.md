# Epic 2 – stacked PR plan

## TL;DR

- Epic 2 ("European advisory sources", scope reduced on 2026-11-01) ships as a **linear stack of 2 PRs** on `wixyvir/cvestream`: `main <- 2.1 <- 2.2`.
- Each PR's base is the previous story's branch, so each PR diff shows **only that story's changes**. The 2.1 PR also carries this plan and the `epic-1: done` status change.
- 2.1 (CERT-EU adapter) and 2.2 (source-drift detection) are in the same sprint wave (wave 8) and only need epic 1 code, so they are created and developed **concurrently**. 2.2 starts from the 2.1 branch at the plan commit, and is **rebased onto the final 2.1 branch** after 2.1 is reviewed, then reviewed itself.
- Each PR goes through three automated steps: `bmad-create-story` (story file + draft PR), `bmad-dev-story` (implementation pushed on the PR), `bmad-code-review` (patches applied, open decisions posted as inline review comments, PR marked ready).
- You test the PRs one at a time, bottom-up: `git switch <branch>`, run the gates, then the manual checks listed per story below.
- Look at the inline review comments marked "decision needed" on each PR: they are the choices the agent did not make for you.
- Merge bottom-up only, with a regular merge (not squash). After 2.1 merges, retarget the 2.2 PR to `main` (automatic if the head branch is deleted).
- PR numbers are not known yet. This document refers to PRs by story and branch.

| Story | Branch | PR base | Depends on (sprint-status) | What it adds |
|---|---|---|---|---|
| 2.1 | `story-2-1-cert-eu-adapter` | `main` | 1.4, 1.5 | `sources/cert_eu.py` (advisories RSS, latest 10, plus the JSON of each new or revised advisory; XML parsed without entity resolution), **one `SourceRecord` per CVE** (`record_id` `<serial>:<CVE>`, aliases = the CVE + `CERT-EU-SA<serial>`; an advisory without CVE gives one advisory-only record), affected products from the `# Affected Products` bullets, `published_at` from the front-matter `original_date`, `updated_at` from `publish_date` (UTC), cursor = latest RSS `pubDate`; registry and settings entry (`sources.cert_eu`), fixtures in `tests/fixtures/cert_eu/`, contract tests with `live` variants, PHP2Shell pipeline replay test, `docs/sources.md`, `settings.example.yaml` |
| 2.2 | `story-2-2-source-drift-detection` | 2.1 branch (after rebase) | 1.4 | `.github/workflows/source-drift.yml` (nightly `schedule` + `workflow_dispatch`, runs the `live` contract tests, on failure opens or updates **one** issue labelled `source-drift`), least-privilege `permissions:` (`contents: read`, `issues: write`), actions pinned by SHA, `timeout-minutes`; `docs/operations.md` section on `source-drift` issues |

### Why 2.1 and 2.2 are developed in parallel, then serialized

`sprint-status.yaml` puts 2.1 and 2.2 in the same wave (wave 8): 2.1 needs 1.4 and 1.5, 2.2 needs only 1.4, and both are on `main`. They are therefore created and developed **concurrently**. That saves one full create/dev/review cycle.

To keep the stack linear, 2.2 is **branched from `story-2-1-cert-eu-adapter` at the plan commit** (this document and the sprint-status change), not from `main`, so its PR diff never shows the plan. Once 2.1 is reviewed, 2.2 is rebased onto the final 2.1 branch, its PR base stays `story-2-1-cert-eu-adapter`, and only then is 2.2 reviewed. Expected conflicts, as listed in `sprint-status.yaml`: few shared files (`docs/sources.md` in 2.1 vs `docs/operations.md` in 2.2, possibly `README.md`), plus `sprint-status.yaml` status lines. 2.2 adds no Python dependency, so `uv.lock` should not conflict; if it does, regenerate it with `uv lock`.

Side effect of the order: once 2.2 sits on top of 2.1, the nightly workflow also runs the CERT-EU `live` contract tests that 2.1 adds. The 2.2 review checks that the workflow selects tests by the `live` marker (not by a hard-coded list of sources), so new adapters are covered without editing the workflow.

## 2. How the PRs are produced

Each story goes through three autonomous steps, in this order:

1. **`bmad-create-story`**: writes the story file `_bmad-output/implementation-artifacts/<story-key>.md` (ACs, tasks, dev notes drawn from the architecture), sets the story to `ready-for-dev` in `sprint-status.yaml` (and `epic-2` to `in-progress`), commits it (`docs(story-2.x): ...`) on the story branch and opens a **draft PR** against its base. Title follows Conventional Commits with the story ID, e.g. `feat(story-2.1): add the CERT-EU adapter`.
2. **`bmad-dev-story`**: implements the tasks on the same branch, with commits separated by concern (`feat(story-2.x)`, `test(story-2.x)`, `docs(story-2.x)`, `chore(story-2.x)`, `ci(story-2.x)`), runs the local gates, sets the story to `review` and pushes to the same PR.
3. **`bmad-code-review`**: adversarial review (Blind Hunter, Edge Case Hunter, Acceptance Auditor). Then:
   - clear-cut fixes (**patches**) are applied and pushed as extra commits (`fix(story-2.x): ...`);
   - **findings that need your decision** are posted as **inline PR review comments** on the relevant lines (marked `:factory:`), with the options and the reviewer's recommendation;
   - deferred or dismissed items are listed in the story file's review section;
   - the PR is marked **ready for review**.

Scheduling: 2.1 and 2.2 run steps 1 and 2 at the same time. 2.1 then runs step 3. 2.2 waits for that, is rebased onto the reviewed 2.1 branch (`git push --force-with-lease`), then runs step 3.

Commits are never squashed. Nothing is merged and nothing is pushed to `main` by the automation. Merging is up to you.

## 3. How to test, story by story

Run the stories in stack order. Each branch already contains everything below it.

### Common gates (every story)

```bash
git fetch origin
git switch <branch>
uv sync --locked
uv run ruff check
uv run ruff format --check
uv run ty check
uv run lint-imports
uv run pytest
uv run cvestream config schema --check
uv run cvestream config validate endpoints.example.yaml
docker build --target runtime -t cvestream:test .
```

Expected: all green. `pytest` runs with the network blocked (pytest-socket), and `live` tests are deselected by default. Also check that the PR's CI (`ci.yml`) is green on GitHub, since it is the merge gate.

### 3.1 Story 2.1: CERT-EU adapter

Branch: `story-2-1-cert-eu-adapter`

1. Contract tests on fixtures:
   ```bash
   uv run pytest tests/contract/cert_eu -v
   ls tests/fixtures/cert_eu
   ```
   Expected cases: the multi-CVE revised advisory 2026-018, a single-CVE advisory, an advisory without CVE and a malformed payload, each with a `live` variant shown as deselected. The fixtures look recorded (real RSS and JSON), not hand-written.
2. Per-CVE records: in the 2026-018 test, the adapter emits **three** records, `2026-018:CVE-2026-109618`, `2026-018:CVE-2026-109619` and `2026-018:CVE-2026-115560`, each with exactly two aliases (its CVE and `CERT-EU-SA2026-018`). The advisory without CVE emits one record whose only alias is `CERT-EU-SA<serial>`.
3. Field mapping, read in the tests or in `sources/cert_eu.py`:
   - CVE IDs come from `content_markdown`, affected products from the `# Affected Products` bullets (free text; versions `None` unless `domain/version.py` parses them, so "PHP 8.5 versions prior to 8.5.12" should give a range if the parser handles it, else "versions unknown");
   - the description is the JSON `description`, the link is the advisory page;
   - `published_at` is the front-matter `original_date` (date only, as UTC), `updated_at` is `publish_date` read as UTC (`23-10-2026 14:36:26` gives `2026-10-23T14:36:26+00:00`, not 16:36);
   - no score: CVSS is `None`, never `0`.
4. XML safety: the RSS is parsed without entity resolution (e.g. `defusedxml`, or a parser with entities off). A test feeds an XML with an external entity or a "billion laughs" payload and the adapter rejects it or ignores the entity. If a new dependency was added, it shows in `pyproject.toml` and `uv lock --check` passes.
5. Revisions and cursor: a new RSS `pubDate` for a known advisory triggers a new JSON fetch, and the CVE added by the revision gets its own record. An unchanged `pubDate` triggers no JSON fetch. The cursor (`next_cursor`) is the latest RSS `pubDate` seen, taken from source data, not from the clock. A source-level failure raises a `SourceError` subclass and leaves the cursor as it was.
6. PHP2Shell pipeline replay:
   ```bash
   uv run pytest tests/integration -v -k "cert_eu or php2shell"
   ```
   Expected: the CERT-EU records publish one `new` item per CVE with an unknown score; the later EUVD records merge into them and publish an `[UPDATE]` on the `unknown` → `critical` band rise; three CVEs stay three vulnerabilities; the log has no `publish.skipped`. A second run of the same advisory revision publishes nothing (FR-19).
7. Settings and registry: `settings.example.yaml` has a `sources.cert_eu` block (`enabled`, `interval`, with the `CVESTREAM_SOURCES__CERT_EU__*` env names). `CVESTREAM_SOURCES__CERT_EU__INTERVAL=PT61M uv run cvestream poll --once` is rejected (interval above 60 minutes, NFR-1).
8. Optional, needs network:
   ```bash
   uv run pytest -m live tests/contract/cert_eu -v
   ```
   should pass, or fail with a clear contract message. Then a real cycle with a scratch data dir:
   ```bash
   cp endpoints.example.yaml /tmp/cvs-endpoints.yaml   # add a `php` product to one endpoint
   CVESTREAM_DATA_DIR=/tmp/cvs-data uv run cvestream poll --once
   ```
   (Exact setting names are in `docs/configuration.md`.) The `cycle.summary` log line lists `cert_eu` with a result. With the daemon running (`uv run cvestream run`), `curl -s localhost:9090/status | jq '.sources'` shows `cert_eu` with its last success and cursor.
9. Docs: `docs/sources.md` has a CERT-EU section (RSS + JSON, payload assumptions, UTC dates, one record per CVE, advisory without CVE, revisions). `README.md` lists CERT-EU as a source. `architecture.md` and `project-context.md` need no change unless the story changed a pattern.
10. Plan commit: this file and `sprint-status.yaml` (`epic-1: done`) are the first commit of the PR.

### 3.2 Story 2.2: source-drift detection

Branch: `story-2-2-source-drift-detection`

1. Rebase sanity check: the PR diff against `story-2-1-cert-eu-adapter` contains only 2.2 changes (the workflow, `docs/operations.md`, the story file and its status line), and the branch contains every reviewed 2.1 commit (`git log --oneline origin/story-2-1-cert-eu-adapter..origin/story-2-2-source-drift-detection`).
2. Read `.github/workflows/source-drift.yml`:
   - triggers: `schedule` (a nightly cron) and `workflow_dispatch`;
   - `permissions:` limited to `contents: read` and `issues: write` (top-level `permissions: {}` or per-job), `timeout-minutes` set on the job;
   - every third-party action pinned by commit SHA with the version in a comment, using the same SHAs as `ci.yml` for `actions/checkout` and `astral-sh/setup-uv`; `persist-credentials: false` on checkout;
   - the tests are selected by marker (`uv run pytest -m live tests/contract`), so EUVD, CISA KEV and the CERT-EU tests from 2.1 all run;
   - the failure step runs only on failure, searches for an **open** issue labelled `source-drift` and comments on it, or opens one if none exists (never one issue per night), and puts the failing test names in the body. It uses `GITHUB_TOKEN`, no extra secret.
3. Lint the workflow if you have the tools: `actionlint .github/workflows/source-drift.yml` (and `zizmor` if installed). No finding on permissions, pinning or template injection (failing test names must not be interpolated straight into a `run:` script).
4. Run the live tests locally the way the workflow does:
   ```bash
   uv run pytest -m live tests/contract -v
   ```
   They pass, or fail with a clear message per source.
5. GitHub checks. `workflow_dispatch` only works once the file is on the default branch, so these run **after the merge to `main`**:
   - create the label if the workflow does not: `SSL_CERT_FILE=$HOME/ca.pem gh label create source-drift --repo wixyvir/cvestream` (check what `docs/operations.md` says);
   - green path: `SSL_CERT_FILE=$HOME/ca.pem gh workflow run source-drift.yml --repo wixyvir/cvestream`, then `gh run watch`: green, no issue opened;
   - failure path: push a throwaway branch where one `live` test fails (e.g. a wrong expected field), then `gh workflow run source-drift.yml --ref <throwaway-branch>` twice. Expected: **one** open issue labelled `source-drift` after the first run, updated (comment) by the second, not a second issue. Delete the throwaway branch and close the issue afterwards.
6. `docs/operations.md` explains what a `source-drift` issue means (an upstream API or payload changed, or the source is down), how to triage it (run `uv run pytest -m live tests/contract -v` locally, compare with the recorded fixtures, update the adapter and fixtures), and how to close it (fix merged, next nightly run green, close by hand).

### What to look at in the review comments (every PR)

- **Inline comments marked as needing a decision** (`:factory:`): each one states the issue, the options and the reviewer's recommendation. Reply on the thread with your choice. Agreed changes go in as extra commits on that branch (then see section 4).
- **Patch commits** (`fix(story-2.x): ...`) added by the review: skim them to check that they are fixes and not scope creep.
- **Story file** `_bmad-output/implementation-artifacts/<story-key>.md`: the "Review Findings" / deferred section, the Dev Agent Record and the File List against the PR diff.
- Points that most likely need a human decision, by story: 2.1 the XML parser choice (new dependency or not), how much of the free-text `# Affected Products` bullets `domain/version.py` should parse, the cursor semantics when the RSS rotates (latest 10 only) and the advisory-only item for a pre-announcement without CVE; 2.2 the cron time, the issue body format and whether the workflow creates the `source-drift` label itself.

## 4. Merge order and propagation

**Merge bottom-up only:** 2.1, then 2.2. Each merge needs a green `ci.yml`. Use a regular merge (not squash) so that 2.2 keeps sharing history with `main`.

**After merging 2.1 into `main`:**
- If "Automatically delete head branches" is enabled (or you delete the branch after merge), GitHub retargets the 2.2 PR to `main` automatically.
- Otherwise, retarget it by hand: `SSL_CERT_FILE=$HOME/ca.pem gh pr edit story-2-2-source-drift-detection --base main --repo wixyvir/cvestream`.

**If 2.1 changes after 2.2 exists** (review fix, decision applied), rebase 2.2:

```bash
git fetch origin
git switch story-2-2-source-drift-detection
git rebase origin/story-2-1-cert-eu-adapter
# on a uv.lock conflict: take the base's version, then regenerate
git checkout --ours uv.lock && uv lock && git add uv.lock && git rebase --continue
uv sync --locked && uv run pytest
git push --force-with-lease
```

- During a rebase, `--ours` is the branch being rebased onto (the base). Keep that `uv.lock`, run `uv lock`, then continue. Never merge `uv.lock` by hand.
- On a `sprint-status.yaml` conflict, keep both stories' status lines (2.1 from the base, 2.2 from the rebased branch).
- If 2.1 was **rewritten** (rebased, or squash-merged into `main`), use `--onto` so that the old commits are not replayed:
  ```bash
  git rebase --onto origin/main <old-2.1-tip> story-2-2-source-drift-detection
  ```
- Always push with `git push --force-with-lease`, never plain `--force`. Never push to `main`.
- After both merges, set `epic-2: done` in `sprint-status.yaml` (and run the optional retrospective) before starting epic 3.

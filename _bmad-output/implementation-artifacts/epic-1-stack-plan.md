# Epic 1 – stacked PR plan

## TL;DR

- Epic 1 ("Filtered vulnerability feed from EUVD and KEV") ships as a **linear stack of 6 PRs** on `wixyvir/cvestream`: `main <- 1.1 <- 1.2 <- 1.3 <- 1.4 <- 1.5 <- 1.6`.
- Each PR's base is the previous story's branch, so each PR diff shows **only that story's changes**.
- 1.3 (YAML config) and 1.4 (EUVD/KEV ingestion) are both built from 1.2 in parallel (sprint wave 3), then 1.4 is rebased onto 1.3 to keep the stack linear.
- Each PR goes through three automated steps: `bmad-create-story` (story file + draft PR), `bmad-dev-story` (implementation pushed on the PR), `bmad-code-review` (patches applied, open decisions posted as inline review comments, PR marked ready).
- You test the PRs one at a time, bottom-up: `git switch <branch>`, run the gates (`uv sync --locked`, ruff, ty, lint-imports, pytest, docker build), then the manual checks listed per story below.
- Look at the inline review comments marked "decision needed" on each PR: they are the choices the agent did not make for you.
- Merge bottom-up only. After each merge, the next PR is retargeted to `main`, either automatically when the merged branch is deleted, or by hand.
- If a lower PR changes, rebase every upper branch in order, regenerate `uv.lock` with `uv lock` (never merge it by hand), then `git push --force-with-lease`.
- PR numbers are not known yet. This document refers to PRs by story and branch.

### Why 1.3 and 1.4 are developed in parallel, then serialized

`sprint-status.yaml` puts 1.3 and 1.4 in the same wave (wave 3): both only need 1.2. They are therefore created and developed **concurrently, each branched from the 1.2 branch**. That saves one full create/dev/review cycle.

To keep the stack linear (one PR = one story diff, merged bottom-up), **1.4 is then rebased onto 1.3** and its PR base is set to `story-1-3-endpoint-configuration-in-yaml`. Expected conflicts, as listed in `sprint-status.yaml`: `pyproject.toml`, `uv.lock`, `settings.py`, `cli/main.py`. `uv.lock` is resolved by taking 1.3's version and re-running `uv lock`, never by editing it by hand. 1.5 needs both 1.3 and 1.4, so it starts from the rebased 1.4 branch.

## 2. How the PRs are produced

Each story goes through three autonomous steps, in this order:

1. **`bmad-create-story`**: writes the story file `_bmad-output/implementation-artifacts/<story-key>.md` (ACs, tasks, dev notes drawn from the architecture), sets the story to `ready-for-dev` in `sprint-status.yaml`, commits it (`docs(story-1.x): ...`) on the story branch and opens a **draft PR** against the previous story's branch. Title follows Conventional Commits with the story ID, e.g. `feat(story-1.1): initialize project skeleton`.
2. **`bmad-dev-story`**: implements the tasks on the same branch, with commits separated by concern (`feat(story-1.x)`, `test(story-1.x)`, `docs(story-1.x)`, `chore(story-1.x)`), runs the local gates, sets the story to `review` and pushes to the same PR.
3. **`bmad-code-review`**: adversarial review (Blind Hunter, Edge Case Hunter, Acceptance Auditor). Then:
   - clear-cut fixes (**patches**) are applied and pushed as extra commits (`fix(story-1.x): ...`);
   - **findings that need your decision** are posted as **inline PR review comments** on the relevant lines (marked `:factory:`), with the options and the reviewer's recommendation;
   - deferred or dismissed items are listed in the story file's review section;
   - the PR is marked **ready for review**.

Commits are never squashed. Nothing is merged and nothing is pushed to `main` by the automation. Merging is up to you.

## 3. How to test, story by story

Run the stories in stack order. Each branch already contains everything below it.

### Common gates (every story)

```bash
git fetch origin
git switch <branch>
uv sync --locked
uv run ruff check
uv run ruff format --check
uv run ty check
uv run lint-imports
uv run pytest
```

Expected: all green. `pytest` runs with the network blocked (pytest-socket), and `live` tests are deselected by default. Also check that the PR's CI (`ci.yml`) is green on GitHub, since it is the merge gate.

From 1.3 on, also check that the committed schema is fresh: `uv run cvestream config schema` followed by `git status` should show no change to `schemas/config-v1.json`.

### 3.1 Story 1.1: project skeleton, container and CI

Branch: `story-1-1-project-skeleton-container-and-ci`

1. `uv run cvestream --help` prints the Typer root help. `uv run python -m cvestream --help` does the same through `__main__.py`.
2. `cat .python-version` shows `3.14`. In `pyproject.toml`, check that the build backend is `uv_build`, that ruff selects `DTZ`, `BLE` and `S`, that pytest declares the `live` and `valkey` markers, and that import-linter allows only `packaging` as a third-party import in `domain`.
3. `docker build --target runtime -t cvestream:test .` succeeds. Then:
   - `docker run --rm cvestream:test --help` prints the CLI help (`ENTRYPOINT ["cvestream"]`);
   - `docker run --rm --entrypoint id cvestream:test` shows `uid=999`;
   - `docker run --rm --entrypoint sh cvestream:test -c 'command -v uv'` prints nothing (no uv in runtime);
   - `docker inspect cvestream:test --format '{{.Config.ExposedPorts}} {{.Config.Volumes}}'` shows `8080/tcp`, `9090/tcp` and `/data`.
4. `docker build --target dev .` succeeds. `docker compose config` is valid. `docker compose watch` starts the `dev` target (there is no daemon yet, so it may only print help or exit; the point is that the build and watch wiring work).
5. Settings: `CVESTREAM_SOURCES__EUVD__INTERVAL=...` with a value above 60 minutes is rejected (see the unit tests in `tests/unit/test_settings.py` for the exact syntax). A value at or below 60 is accepted, and the default is 15 min.
6. `.dockerignore` excludes `_bmad/`, `_bmad-output/` and `.claude/`. `.github/workflows/ci.yml` pins every Action by SHA (version in a comment) and declares `permissions:`. `.github/dependabot.yml` covers `uv`, `github-actions` and `docker`.
7. `README.md` and `CLAUDE.md` exist, and `CLAUDE.md` points to `architecture.md` and `project-context.md`.

### 3.2 Story 1.2: vulnerability model and matching engine

Branch: `story-1-2-vulnerability-model-and-matching-engine`

1. `uv run lint-imports` passes, and `grep -rn "^import\|^from" src/cvestream/domain/` shows only stdlib, `packaging` and intra-`domain` imports.
2. `uv run pytest tests/unit/domain -v` covers the matcher, version, severity and identity tables.
3. Whole-word matching, quick REPL check:
   ```bash
   uv run python -c "from cvestream.domain import matcher; help(matcher.match)"
   ```
   Then read the matcher tests and check that these cases exist: `php` matches "PHP 8.3" but not "phpMyAdmin"; an exclusion term blocks the entry; an alias matches; the title alone never matches.
4. Unknown data passes through: no score plus `min_cvss` gives a match labelled `score_unknown`; `n/a` or unparseable versions plus `min_version` gives a match labelled `versions_unknown`.
5. Severity: with conflicting scores, the highest wins; no score gives band `unknown`, never `low`.
6. Identity: aliases are upper-cased, and the primary ID follows CVE > EUVD > advisory, never a URL.
7. `version.py` handles `< 8.2.29`, `8.1.0 - 8.3.4`, `n/a` and French free text (the last two give `None`).

### 3.3 Story 1.3: endpoint configuration in YAML

Branch: `story-1-3-endpoint-configuration-in-yaml`

1. `uv run cvestream config validate endpoints.example.yaml; echo $?` prints `0`.
2. Make an invalid copy (unknown field, bad slug such as `My_Team`, or `min_cvss: "high"`):
   ```bash
   cp endpoints.example.yaml /tmp/bad.yaml && echo "  unknown_field: 1" >> /tmp/bad.yaml
   uv run cvestream config validate /tmp/bad.yaml; echo $?
   ```
   Expected: exactly one plain error line on stderr naming the field, and exit code `2`.
3. `uv run cvestream config schema`, then `git diff --exit-code schemas/config-v1.json`: no diff. Change a field description in `config/models.py` without regenerating and check that the CI step (or its local equivalent) fails.
4. The shorthand `php >= 8.2` in a product list is accepted and turns into `name: php`, `min_version: 8.2`.
5. `endpoints.example.yaml` documents every field and holds a token **placeholder**, not a real token.
6. YAML provider revision: loading the same file twice gives the same revision (SHA-256 of the content), and editing one byte changes it (covered by unit tests in `tests/unit/config/`).
7. `docs/configuration.md` describes `settings.yaml`, the `CVESTREAM_*` variables (with `__` nesting and `*_FILE` secrets) and `endpoints.yaml`.

### 3.4 Story 1.4: EUVD and KEV ingestion

Branch: `story-1-4-euvd-and-kev-ingestion`

1. `uv run pytest tests/contract -v` runs normal, missing-score, `n/a`-version and malformed payload cases for `euvd` and `cisa_kev` with respx, and the `live` variants show as deselected.
2. Optional, needs network: `uv run pytest -m live tests/contract -v` hits the real EUVD and CISA KEV APIs. It should pass, or fail with a clear contract message.
3. `ls tests/fixtures/euvd tests/fixtures/cisa_kev`: the fixtures are named after what they show (`euvd_no_score.json`, `euvd_version_na.json`, ...) and look recorded, not hand-written.
4. In `cvestream/http.py`, check `trust_env=False`, explicit timeouts, a response size limit, and retries only on timeout, 5xx and 429 (with `Retry-After`), using capped backoff with jitter. TLS verification is never disabled.
5. EUVD adapter: with no cursor, the first fetch starts at now − 14 days. Placeholders (`""`, `n/a`, unscored `0`) become `None`. EPSS ×100 becomes a fraction. Naive dates become UTC.
6. A record that fails validation is skipped and counted. A source-level failure raises a `SourceError` subclass and does not advance the cursor.
7. `docs/sources.md` documents the timezone, placeholder and pagination assumptions for each source. `sources/registry.py` builds the adapters from settings, with one interval per source.
8. Rebase sanity check: the PR diff against the 1.3 branch contains only 1.4 changes, and `uv lock --check` passes.

### 3.5 Story 1.5: correlation, state and publication decisions

Branch: `story-1-5-correlation-state-and-publication-decisions`

1. `uv run cvestream db migrate` (with a temporary data dir, e.g. `CVESTREAM_DATA_DIR=/tmp/cvs-data`; check `docs/configuration.md` for the exact setting name) creates the SQLite database. Running it again is a no-op.
2. `sqlite3 /tmp/cvs-data/*.db '.tables'` lists `vulnerability`, `alias`, `source_record`, `publication`, `source_cursor` and `alembic_version`. `PRAGMA journal_mode;` returns `wal`.
3. `uv run cvestream db backup /tmp/cvs-backup.db` produces a valid copy (`sqlite3 /tmp/cvs-backup.db '.tables'`).
4. `uv run pytest tests/integration/test_restart_no_repost.py -v` passes. This is the NFR-3 / SM-4 guardrail: a rerun after a restart publishes nothing new.
5. Decision tests: first match gives `new`; becoming KEV gives `kev`; a band rise (including `unknown` → rated) gives `band-{band}`; a score change within the band, a new source or a description edit gives nothing. Late data that produces a first match gives `new`, not an update.
6. The GUID `cvestream:{endpoint_id}:{primary_id}:{kind}` is stored in `publication.guid` and never recomputed. `grep -rn "cvestream:{" src/` should show a single construction site, in the decision code.
7. Correlation: two records sharing a CVE or EUVD ID merge into one vulnerability that keeps every `Sourced` value, and a URL change does not create a duplicate.
8. `grep -rn "commit()" src/cvestream` shows commits only through `state.transaction()`, and `pipeline/run.py` opens exactly one transaction per run.

### 3.6 Story 1.6: feeds served by the daemon

Branch: `story-1-6-feeds-served-by-the-daemon`

1. Local daemon with the YAML provider. Copy `endpoints.example.yaml` to `endpoints.yaml`, put a real token in it (e.g. from `python -c "import secrets; print(secrets.token_urlsafe(32))"`), then:
   ```bash
   CVESTREAM_DATA_DIR=./data uv run cvestream run
   ```
   (Exact setting names are in `docs/configuration.md`.) The logs show the migration, the listeners starting and the source loops starting.
2. Private listener:
   ```bash
   curl -i localhost:9090/healthz        # 200 right away
   curl -i localhost:9090/readyz         # 503 until config + feed cache are loaded, then 200
   curl -s localhost:9090/status | jq    # per-source last success/error/cursor, per-endpoint item count and last render
   uv run cvestream healthcheck --ready; echo $?   # 0 once ready
   ```
3. Public feed:
   ```bash
   curl -i localhost:8080/feeds/<token>.xml           # 200, Content-Type: application/rss+xml; charset=utf-8, ETag, Last-Modified, Cache-Control: max-age=300
   curl -i -H 'If-None-Match: "<etag>"' localhost:8080/feeds/<token>.xml   # 304
   curl -I localhost:8080/feeds/<token>.xml           # HEAD works
   curl -i localhost:8080/feeds/wrong-token.xml       # 404, empty body
   ```
   The access log line carries the `endpoint_id`, **never the token**.
4. Feed content: validate the XML (e.g. `xmllint --noout`). Titles name the matched product and band, updates start with `[UPDATE]`, the body shows CVE/EUVD IDs, per-source CVSS with version, KEV status with list and ransomware use, versions or "versions unknown", and source links. Missing values read `unknown`. Items cover the last 14 days.
5. `uv run cvestream poll --once` runs one cycle, logs one `cycle.summary` (per-source result, per-endpoint published count, unknown-score and unknown-version pass-throughs), then exits.
6. Hot reload: while `run` is up, edit `endpoints.yaml` with a valid change, which applies on the next run without restart. Then make it invalid: you get `config.rejected` and the last valid config stays active. `Ctrl-C` / SIGTERM finishes the current run and stops cleanly.
7. Container: `docker build --target runtime -t cvestream:test .`, then `docker compose -f deploy/compose/compose.yml up` (point it at the local image or wait for the GHCR `edge` tag). Check that only 8080 is published, the root filesystem is read-only, capabilities are dropped, `/data` is a named volume and `docker inspect` shows a healthy `HEALTHCHECK` (`cvestream healthcheck`).
8. `uv run pytest tests/integration/test_pipeline_end_to_end.py -v` goes from recorded fixtures to a served feed. `docs/operations.md` covers running, logs, `/status`, backup and the warning that reverse-proxy logs contain the token. `README.md` has the self-hosted quick start.

## 4. Merge order and propagation

**Merge bottom-up only:** 1.1, then 1.2, 1.3, 1.4, 1.5 and 1.6. Each merge needs a green `ci.yml`. Use a regular merge (not squash) so that the upper branches keep sharing history with `main`.

**After merging a PR into `main`:**
- If "Automatically delete head branches" is enabled (or you delete the branch after merge), GitHub retargets the next PR to `main` automatically.
- Otherwise, retarget it by hand: `SSL_CERT_FILE=$HOME/ca.pem gh pr edit <branch-of-next-story> --base main`.
- Once 1.1 is merged, protect `main` (PRs only, required `ci` check), as the architecture requires.

**If a lower PR changes after upper PRs exist** (review fix, decision applied), propagate upwards in order. For example, after changing 1.2:

```bash
git fetch origin
git switch story-1-3-endpoint-configuration-in-yaml
git rebase origin/story-1-2-vulnerability-model-and-matching-engine
# on a uv.lock conflict: take the base's version, then regenerate
git checkout --ours uv.lock && uv lock && git add uv.lock && git rebase --continue
uv sync --locked && uv run pytest
git push --force-with-lease

git switch story-1-4-euvd-and-kev-ingestion
git rebase origin/story-1-3-endpoint-configuration-in-yaml
# ... same for 1.5 and 1.6
```

- During a rebase, `--ours` is the branch being rebased onto (the base). Keep that `uv.lock`, run `uv lock` so that it re-adds this story's dependencies from `pyproject.toml`, then amend or continue. Never merge `uv.lock` by hand.
- If the lower branch was **rewritten** (rebased, or squash-merged into `main`), use `--onto` so that the old commits are not replayed:
  ```bash
  git rebase --onto origin/main <old-base-commit-or-old-branch-tip> story-1-3-endpoint-configuration-in-yaml
  ```
- Always push with `git push --force-with-lease`, never plain `--force`. Never push to `main`.
- Check that `schemas/config-v1.json` is still fresh after rebasing 1.3 and above (`uv run cvestream config schema && git diff --exit-code`).
